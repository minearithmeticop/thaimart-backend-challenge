# Lottery Search System (System Design Document)

## โจทย์และขอบเขต (Objective & Scope)

* **ขอบเขตข้อมูล:** สลากกินแบ่ง 10,000,000 ใบ เป็นเลข 6 หลักคงที่ (`000000`–`999999`)
* **ฟีเจอร์ค้นหา:** รองรับ Pattern ที่มี Wildcard (`*`) ทุกตำแหน่ง เช่น `****23`, `1****5`, `*2*4*6`
* **เงื่อนไขสำคัญ (The Core Rule):** **สลาก "ใบเดียวกัน" ห้ามถูกขายหรือส่งให้ผู้ใช้สองคนพร้อมกัน**
* *ข้อสังเกต:* เลข 6 หลักมีเพียง 1,000,000 หมายเลข แต่เรามีสลาก 10 ล้านใบ แปลว่า 1 หมายเลขจะมีสลากเฉลี่ย ~10 ใบ (แยกกันตามเล่ม/ชุด)
* ดังนั้น **เลขเดียวกันขายให้คนหลายคนได้ แต่ต้องเป็นสลากคนละใบ**

### สถานการณ์ผู้ใช้จริง (User Scenario)

คุณ A อยากได้เลข `199523` → พิมพ์ค้นหาเต็ม 6 หลัก → ระบบตอบ "เลขนี้ขายหมดแล้ว" (แต่ละเลขมีเพียง ~10 ใบ) → A คลายเงื่อนไขเป็น "ขอลงท้าย 23 ก็ได้" แล้วพิมพ์ `****23`:

```
ค้นหา ****23
   │
   ├─► แสดงสรุป: "พบ 100,000 เลขที่ยังมีสลาก" (นับบิต 1 ทั้ง Bitmap)
   ├─► แสดงรายการเลขที่พร้อมขายแบบแบ่งหน้า ให้เลือกชม
   │      เช่น 100023, 100123, 199923, ... → คลิก 199923 → "เลขนี้เหลือ 7 ใบ"
   └─► หรือกดปุ่ม "ลุ้นเลขให้ฉัน" (Quick Buy) — ให้ระบบสุ่มเลือกให้เลย
                │
                ▼
        ยืนยันคำสั่งซื้อ (1 ใบ หรือหลายใบก็ได้) ──► Allocation Layer: LMOVE หยิบ "ใบจริง" ตามจำนวนที่สั่ง + Hold 10 นาที
```

การซื้อเป็นหน่วย **"ใบ"** เสมอ — ครั้งละ 1 ใบหรือหลายใบก็ได้ (เลขเดียวหลายใบ หรือหลายเลขในตะกร้าเดียว เช่น 199923 × 3 ใบ + 123450 × 2 ใบ) — Pattern ทำหน้าที่เป็น "ตัวกรอง" ให้เจอเลขที่ใช่ เหมือน Filter ของ E-commerce ทั่วไป ไม่ใช่การซื้อทั้งชุดผลลัพธ์ และนี่คือเหตุผลที่ระบบต้องแยกชั้นค้นหา (นับ + แสดงรายการ) ออกจากชั้นจัดสรร (หยิบ "ใบจริง" ตามจำนวนที่สั่ง)

## 1. ภาพรวมสถาปัตยกรรม (System Architecture)

หัวใจของระบบนี้คือ **"แยกงานค้นหา ออกจากงานจองและขาย" (Decoupling)** เพื่อไม่ให้โหลดจากการค้นหาไปรบกวนฐานข้อมูลหลัก

```
[ ผู้ใช้ค้นหา: 1****5 ]
            │
            ▼
┌─────────────────────────────────────────────────────────┐
│ 1. Search Layer (In-Memory Bitmaps บน App Nodes)        │
│    - กรองหาเลขที่ตรงเงื่อนไขด้วย Bitwise AND ภายใน < 0.1 ms     
│    - วิ่งบน RAM 100% ไม่แตะ Disk ไม่ล็อกข้อมูลใดๆ               
└───────────────────────────┬─────────────────────────────┘
                            │ ได้ชุดเลขที่แมตช์ (เช่น 100005, 100015...)
                            ▼
┌─────────────────────────────────────────────────────────┐
│ 2. Allocation Layer (Redis — Atomic Claim)              │
│    - หยิบ "ใบสลากจริง" ออกจากคลังด้วยคำสั่ง Atomic              
│    - กันคนแย่งใบเดียวกันสำเร็จตั้งแต่ระดับ Memory       
│    - ล็อกสิทธิ์ชั่วคราว (Hold) 10 นาทีเพื่อให้ไปจ่ายเงิน 
└───────────────────────────┬─────────────────────────────┘
                            │ จ่ายเงินสำเร็จ (Async Message Queue)
                            ▼
┌─────────────────────────────────────────────────────────┐
│ 3. Source of Truth Layer (MongoDB)                      │
│    - บันทึกสถานะ SOLD ถาวรลง Documents                   
│    - มี Unique Index บน ticket_id เป็นด่านสุดท้ายกันการขายสลากใบเดียวกันซ้ำ (Double-Sell) 
│    - มี Background Worker คอยตรวจสอบและปรับข้อมูล Redis ↔ MongoDB ให้ตรงกันทุก 1 นาที (คืนตั๋วค้างจอง / ล้างตั๋วที่ขายแล้ว)
└─────────────────────────────────────────────────────────┘

```

## 2. ระบบค้นหา Wildcard ด้วย Positional Bitmaps

### 2.1 ทำไมต้องแปลงข้อมูลเป็น Bitmap?

เลข 6 หลักมีแค่ **1,000,000 หมายเลขพอดี** เราจึงแมปหมายเลขสลากเข้ากับ **ตำแหน่งบิต (Bit Offset)** ในหน่วยความจำแบบ $1:1$ ได้ทันที:

```
Bit Offset:      0        1        2    ...     23    ...   123456   ...   999999
Ticket Number: 000000   000001   000002  ...  000023   ...   123456   ...   999999
```

---

### 2.2 โครงสร้างการค้นหา — 60 Bitmap สำหรับค้นหา Pattern + 1 Bitmap สำหรับบอกว่าเลขไหนยังมีสลากขาย

สลากมี 6 ตำแหน่ง (Index 0 ถึง 5) และแต่ละตำแหน่งเป็นได้ 10 ตัวเลข (`0`–`9`) เราจึงสร้าง Bitmap ทั้งหมด **$6 \times 10 = 60$ ตัว** — ทุกตัวยาว 1 ล้านบิตเหมือนกันหมด ต่างกันแค่ว่า "ใครโดนติ๊กเป็น 1":

```
ตำแหน่งที่ (Position):
  Pos 0 (หลักแสน)  ──► [Bitmap 0] [Bitmap 1] [Bitmap 2] ... [Bitmap 9]   (10 ตัว)
  Pos 1 (หลักหมื่น)  ──► [Bitmap 0] [Bitmap 1] [Bitmap 2] ... [Bitmap 9]   (10 ตัว)
  Pos 2 (หลักพัน)   ──► [Bitmap 0] [Bitmap 1] [Bitmap 2] ... [Bitmap 9]   (10 ตัว)
  Pos 3 (หลักร้อย)  ──► [Bitmap 0] [Bitmap 1] [Bitmap 2] ... [Bitmap 9]   (10 ตัว)
  Pos 4 (หลักสิบ)   ──► [Bitmap 0] [Bitmap 1] [Bitmap 2] ... [Bitmap 9]   (10 ตัว)
  Pos 5 (หลักหน่วย) ──► [Bitmap 0] [Bitmap 1] [Bitmap 2] ... [Bitmap 9]   (10 ตัว)
```

```
ขนาดหน่วยความจำ = 60 Bitmap × 122 KB ≈ 7.32 MB เท่านั้น
(ขนาดเล็กมากจนโหลดไว้บน L3 Cache ของ CPU หรือ RAM ของทุกเครื่องได้สบาย)

```

#### แล้ว Bitmap ทั้ง 61 ตัวทำหน้าที่อะไร?

1. **60 Bitmap แรก — ไว้ค้นหา Pattern:** แต่ละตัวบอกว่า "เลขไหนมีเลขนี้อยู่ที่หลักนี้" (เช่น Bitmap [หลักแสน = 1] จะเช็ค 1 ไว้ทุกเลขช่วง 100000–199999) ค่าเหล่านี้ไม่มีวันเปลี่ยน (Immutable) จึงสร้างครั้งเดียวตอน Boot แล้วทุก Server ถือสำเนาเหมือนกันหมด **ไม่ต้องซิงก์กันเลยตลอดอายุระบบ**
2. **Bitmap ตัวที่ 61 — บอกว่าเลขไหนยังมีสลากขาย (Availability Bitmap):** เช็ค 1 = ยังมีของ, 0 = ขายหมดแล้ว เป็นตัวเดียวที่ถูกอัปเดตเมื่อสลากขายหมดหรือมีคนคืนสลาก

ตัวอย่างหน้าตาของ Bitmap ตัวที่ 61 (ยืมเลขจาก Walkthrough หมวด 2.4):

```
[Availability Bitmap — ตัวที่ 61]
   Offset 100005: 1   ──► เลขนี้ยังมีสลากขาย (คลังเหลือ ~10 ใบ)
   Offset 100015: 1   ──► ยังมีสลากขาย
   Offset 199995: 0   ──► ขายหมดแล้ว — เลขนี้จะไม่โผล่ในผลค้นหาอีก
```

เมื่อเอาไป AND ต่อจากผลของ Pattern: `1****5` เดิมแมตช์ 100005, 100015, 199995 — แต่พอ AND กับ Bitmap ตัวนี้จะเหลือเพียง 100005 กับ 100015 เท่านั้น เพราะ 199995 หมดสต็อกไปแล้ว

วงจรของบิตหนึ่งตัว: ใบสุดท้ายของ `199995` ถูกจอง → เปลี่ยนบิตเป็น 0 → ค้นหาไม่เจอ → ถ้าผู้จองไม่ชำระเงินภายใน 10 นาที ระบบคืนสลากเข้าคลัง → เปลี่ยนบิตกลับเป็น 1 → ค้นหาเจอได้อีก (รายละเอียดหมวด 3.2 และ 4)

#### แล้ว Bitmap ทั้ง 61 ตัวมาจากไหน สร้างเมื่อไหร่?

**60 Bitmap หลัก — สร้างเองตอน Boot ด้วยคณิตศาสตร์ล้วน ไม่ต้องดึงข้อมูลจากที่ไหนเลย:**

```
// รันครั้งเดียวตอนสตาร์ท service จบในหลักมิลลิวินาที
for เลข := 0; เลข < 1,000,000; เลข++ {
    for ตำแหน่ง := 0; ตำแหน่ง < 6; ตำแหน่ง++ {
        หลัก := ดึงเลขหลักที่ ตำแหน่ง ของ เลข      // คณิตศาสตร์ล้วน เช่น (เลข ÷ 10^n) mod 10
        setBit(Bitmap[ตำแหน่ง][หลัก], เลข)
    }
}
```

เพราะ "เลข 100005 มี 1 หลักแสน" เป็นความจริงทางคณิตศาสตร์ ไม่ใช่ข้อมูลที่ต้องเก็บ — จึงไม่มีขั้นตอน "โหลดข้อมูลจาก Redis มาสร้าง Bitmap" ทุก App Node จึงมี Bitmap ชุดเหมือนกันหมดโดยไม่ต้องซิงก์กันเลย

**Availability Bitmap + คลังใบสลากใน Redis — สร้างครั้งแรกจาก MongoDB** (ใช้วิธีเดียวกันตอนกู้คืนระบบตามหมวด 5):

```
// ครั้งแรกของระบบ หรือตอน Redis ขาดหาย
for ตั๋ว in MongoDB.find(status ≠ SOLD):
    RPUSH num:{ตั๋ว.ticket_number} ตั๋ว._id       // ใส่ใบเข้าชั้นเก็บของเลขนั้น
    SETBIT availBitmap {ตั๋ว.ticket_number} 1     // เปิดบิตว่าเลขนี้ยังมีของ
```

### 2.3 ตรรกะการค้นหา (Search Mechanism)

ในทางตรรกศาสตร์บูลีน เครื่องหมาย Wildcard (`*`) หมายถึง "เป็นตัวเลขใดก็ได้ (0–9)" ซึ่งเทียบเท่ากับค่าความจริง $\text{True}$ (บิตเป็น 1 ทุกตำแหน่ง) เราจึงไม่ต้องนำตำแหน่งที่เป็น `*` มาคำนวณ กฎการคำนวณจึงมีแค่ 2 ข้อ:

1. หากตำแหน่งเป็น **ตัวเลข (0–9)** $\rightarrow$ ดึง Bitmap ของตำแหน่งและตัวเลขนั้นมาทำ `AND`
2. หากตำแหน่งเป็น **Wildcard (`*`)** $\rightarrow$ ข้าม (Skip) ไม่ต้องดึง Bitmap

---

### 2.4 ตัวอย่างการทำงานจริงทีละขั้นตอน (Walkthrough)

#### ตัวอย่างที่ 1: Pattern `1****5` (ขึ้นต้นด้วย 1 ลงท้ายด้วย 5)

```
Pattern:       1       *       *       *       *       5
Position:    Pos 0   Pos 1   Pos 2   Pos 3   Pos 4   Pos 5
Action:        ดึง      ข้าม     ข้าม      ข้าม     ข้าม     ดึง
```

```
[Bitmap Pos 0 = 1]   (เลข 100000–199999 มีบิตเป็น 1)
   Offset 000005: 0
   Offset 100000: 1
   Offset 100005: 1
   Offset 199995: 1
   Offset 200005: 0

            AND (Bitwise AND)

[Bitmap Pos 5 = 5]   (เลขลงท้ายด้วย 5 ทุกตัวมีบิตเป็น 1)
   Offset 000005: 1
   Offset 100000: 0
   Offset 100005: 1
   Offset 199995: 1
   Offset 200005: 1

            EQUALS (=)

[Result Bitmask]
   Offset 000005: 0  (0 AND 1 = 0)
   Offset 100000: 0  (1 AND 0 = 0)
   Offset 100005: 1  (1 AND 1 = 1) ──► แมตช์!
   Offset 199995: 1  (1 AND 1 = 1) ──► แมตช์!
   Offset 200005: 0  (0 AND 1 = 0)
```

#### ตัวอย่างที่ 2: Pattern `**34*9`

* ตำแหน่ง 0, 1, 4 เป็น `*` $\rightarrow$ ข้าม
* ดึงเพียง 3 ตัวมาทำ Intersection:

$$\text{Result} = \text{Bitmap}(\text{Pos 2}=3) \ \mathbf{AND} \ \text{Bitmap}(\text{Pos 3}=4) \ \mathbf{AND} \ \text{Bitmap}(\text{Pos 5}=9)$$

ทุก Pattern จะถูก `AND` กับ Availability Bitmap อีกหนึ่งชั้นเสมอ เพื่อเหลือเฉพาะเลขที่ยังมีสลากขาย:

$$\text{ผลลัพธ์สุดท้าย} = \text{Result ของ Pattern} \ \mathbf{AND} \ \text{Bitmap}[\text{ยังมีสลากขาย}]$$

---

### 2.5 ทำไมวิธีนี้จึงเร็วมาก

CPU ยุคปัจจุบันประมวลผลคำสั่ง Bitwise บน Register ขนาด 64-bit ถึง 512-bit ได้ใน **1 Clock Cycle** การนำบิต 1 ล้านช่องมา AND กัน จึงใช้คำสั่งเพียง $1{,}000{,}000 \div 64 = 15{,}625$ ครั้ง เสร็จได้ในเวลา **< 0.05 ms**

## 3. กลยุทธ์การจัดสรรสลากและป้องกันคนแย่งกัน (Allocation Strategy)

### 3.1 จุดตายที่ต้องระวัง: ห้ามล็อกที่ระดับ Pattern

สมมติผู้ใช้ A ค้นหา `****23` และผู้ใช้ B ค้นหา `123***`

* ทั้งสองคนมีสิทธิ์แมตช์เจอเลข **`123023`** เหมือนกัน
* ถ้าเราไปทำ Distributed Lock ที่ชื่อ Pattern (`lock:****23`) จะไม่มีประโยชน์ เพราะไม่ได้กันผู้ใช้ B
* **บทสรุป:** ระบบต้องตัดสินการแย่งกันที่ **ระดับ "ใบสลากจริง" (Ticket ID)** เท่านั้น

---

### 3.2 กลไก Atomic Claim บน Redis

จัดโครงสร้างคลังสลากใน Redis:

* `num:{เลข}` (Redis List): เก็บ Ticket ID ของเลขนั้น ๆ (เฉลี่ย ~10 ใบต่อเลข)
* `hold:{ticket_id}` (Redis String): บันทึกว่าใครเป็นคนจอง พร้อมตั้งเวลาหมดอายุ (TTL 10 นาที)

```
คลังกลางใน Redis — ทุก Pattern หยิบจากคลังเดียวกัน (จัดเก็บแยกชั้นตามเลข)
num:123023 = [ #101, #102, #105, ... ]   (เฉลี่ย ~10 ใบต่อเลข)

[ ผู้ใช้ A: ค้นหา ****23 ] ──► ไปหยิบที่ชั้น 123023 ──► LMOVE ──► ได้ใบ #101 (ใบหายจากคลังทันที)
[ ผู้ใช้ B: ค้นหา ****23 ] ──► มาถึงชั้นเดียวกันพร้อมกันเป๊ะ ──► LMOVE ──► ได้ใบ #102
      Redis จ่ายคนละใบให้เอง — Pop จาก List เดียวกันสองครั้ง ไม่มีทางได้ใบเดียวกัน
[ ผู้ใช้ C: ค้นหา 123*** ] ──► เลือกเลข 123023 ก็ได้ (ซ้อนทับกับ A) ──► LMOVE ──► ได้ใบ #105
      ได้ "เลขเดียวกับ A" ได้ — แต่คนละ "ใบ" ซึ่งถูกต้องตาม Core Rule

```

หมายเหตุ: ในชีวิตจริง A กับ B มักไม่ชนกันอยู่แล้ว (Pattern เดียวแมตช์เป็นแสนใบ + สุ่มลำดับ) — ภาพนี้แสดง "จังหวะชน" เช่นเลขฮอตหรือใบสุดท้ายของเลข ซึ่งเป็นจังหวะที่ Atomic Pop พิสูจน์คุณค่า

#### ขั้นตอนการจัดสรร (Allocation Flow):

1. **Search:** กรองเลขที่ตรงเงื่อนไขจาก In-Memory Bitmap (ได้ชุดหมายเลขผู้เข้ารอบ)
2. **Atomic Pop:** สุ่มหยิบเลขขึ้นมา แล้วใช้คำสั่ง `LMOVE` (หรือ `SPOP`) ดึง Ticket ID ออกมาจาก List ของเลขนั้น คำสั่งนี้เป็น Atomic ในตัว ใครมาก่อนได้ก่อน 100%
3. **Hold:** เมื่อได้ตั๋วมา ให้สร้าง Key `hold:{ticket_id}` พร้อม TTL 10 นาที เพื่อให้ผู้ใช้ไปชำระเงิน
4. **Out of Stock Check:** ถ้าสลากของเลขนั้นถูกดึงจนหมด ให้เปลี่ยนบิตของเลขนั้นใน **Availability Bitmap เป็น 0** เพื่อให้คนอื่นค้นหาไม่เจออีก

**การซื้อหลายใบในคำสั่งซื้อเดียว:** ผู้ใช้จริงมักซื้อทีละหลายใบ (เลขเดียวหลายใบ หรือหลายเลขในตะกร้า) กลไกเดิมรองรับได้ทันที — ทำซ้ำ Atomic Pop ตามจำนวนที่สั่ง (แต่ละครั้งยัง Atomic เหมือนเดิม) และหากธุรกิจต้องการ **All-or-Nothing** (ตะกร้าสำเร็จทั้งหมดหรือยกเลิกทั้งหมด ไม่มีสถานะครึ่งๆ กลางๆ) ให้รวมการ Pop ทั้งตะกร้าเป็น **Lua Script ชุดเดียว** — Redis รัน Lua แบบ Atomic: เช็คจำนวนคงเหลือ (LLEN) ของทุกเลขในตะกร้าก่อน พอทั้งหมดจึง Pop ทีเดียว ไม่พอคืนทั้งหมด

---

### 3.3 ทำไมใช้ Redis ถึงเหมาะกว่าการให้ MongoDB ทำ Atomic Update โดยตรง?

* แม้ MongoDB จะมีคำสั่ง Atomic อย่าง `findOneAndUpdate` แต่ตอนช่วงใกล้หวยออกที่มีคนค้นหาและกดจองพร้อมกันหลายแสน Request การวิ่งเข้าไปยิง Write Lock ลง MongoDB Document โดยตรงจะทำให้ Disk I/O และ CPU ของ Database รับภาระหนักเกินจำเป็น
* Redis ทำงานบนหน่วยความจำ คำสั่ง `LMOVE` ใช้เวลา $O(1)$ รองรับได้หลัก 100,000+ ops/sec ต่อเครื่อง จึงใช้เป็นแนวหน้าปะทะแรงกระแทกได้ดีกว่ามาก แล้วปล่อยให้ MongoDB ทำหน้าที่เก็บข้อมูลความจริงอย่างเงียบๆ

## 4. วงจรการซื้อและการคืนสลาก (State Machine & Rollback)

```
              ┌────────────────────────────────────────┐
              │                                        │ (หมดเวลา 10 นาที / กดยกเลิก)
              ▼                                        │ คืนสต็อกกลับเข้าระบบ
     ┌────────────────┐     (1) จองสำเร็จ       ┌────────────────┐
     │   AVAILABLE    │ ────────────────────► │    RESERVED    │
     └────────────────┘                       └────────────────┘
                                                       │
                                                       │ (2) ชำระเงินสำเร็จ
                                                       ▼
                                               ┌────────────────┐
                                               │      SOLD      │
                                               └────────────────┘

```

### การจัดการเมื่อหมดเวลาชำระเงิน (Reservation Timeout):

1. หากผู้ใช้ไม่ชำระเงินภายใน 10 นาที Key `hold:{ticket_id}` จะหมดอายุ
2. Background Worker จะตรวจจับรายการหมดอายุ แล้วนำ Ticket ID คืนกลับเข้า List `num:{เลข}` ใน Redis
3. หากเลขนั้นสต็อกเคยหมดไป (0 ใบ) แล้วฟื้นกลับมามีของ (1 ใบ) ให้ทำการ **เปิดบิตใน Availability Bitmap กลับเป็น 1 (แก้แค่ Bitmap เดียว)**
4. เลขนั้นจะกลับมาค้นหาเจอได้ใหม่ทันทีแบบ Real-time

## 5. ฐานข้อมูลหลักและการกู้คืนระบบ (Source of Truth & Recovery)

แม้ Redis จะเร็วและจัดการ Concurrency ได้ดี แต่เรา **ไม่ใช้ Redis เป็นแหล่งเก็บข้อมูลถาวร**:

### โครงสร้าง Document บน MongoDB (`tickets` Collection)

```json
{
  "_id": "TICKET_101",
  "ticket_number": "045823",
  "book_id": 12,
  "status": "SOLD",
  "user_id": "user_abc",
  "sold_at": "2026-08-24T10:00:00Z",
  "order_id": "ORD_999"
}

```

* **MongoDB คือ Source of Truth:** เมื่อชำระเงินสำเร็จ ระบบจะส่ง Event ไปบันทึกสถานะใน MongoDB เป็น `status: 'SOLD'`
* **Unique Index ป้องกันการขายซ้ำ:** สร้าง Index `{ ticket_number: 1, book_id: 1 }` แบบ Unique เพื่อเป็นด่านสุดท้ายระดับ Database ให้มั่นใจว่าจะไม่มีการบันทึกสลากใบเดียวกันซ้ำแน่นอน
* **Reconciliation Worker:** มี Background Job คอยตรวจสอบและปรับข้อมูลระหว่าง Redis กับ MongoDB ให้ตรงกันทุก 1 นาที เพื่อดึงสลากที่ค้างหรือหลุดจองกลับเข้าคลัง
* **Disaster Recovery:** หาก Redis ดับ ให้ Promote Replica ขึ้นมาแทนก่อน (ใช้เวลาวินาที) ส่วนการ Rebuild จาก MongoDB คือแผนสุดท้ายเมื่อข้อมูลหายทั้งคู่ — อ่านแบบ Streaming + Pipeline และแบ่งช่วงเลขให้ทำขนาน (คีย์แยกตามเลขอยู่แล้วจึงไม่ชนกัน) สำหรับ 10 ล้านใบจบในระดับ 1 นาที และโดยปกติงานนี้คือ batch job เตรียมคลังก่อนเปิดขายแต่ละงวด ไม่ใช่งานที่เกิดตอนมีผู้ใช้กำลังใช้งาน

## 7. สรุปจุดเด่นและข้อแลกเปลี่ยน (Summary & Trade-offs)

### จุดเด่น (Key Strengths)

1. **ความเร็วคงที่เสมอ (Deterministic Speed):** ไม่ว่าจะค้นหาแบบระบุหัวท้าย (`1****5`) หรือสลับฟันปลา (`*2*4*6`) ความเร็วในการค้นหาก็เท่ากันหมด ($< 0.1 \text{ ms}$) เพราะใช้ Bitmap ขนาดคงที่
2. **ประหยัดทรัพยากรสูงสุด:** จัดการข้อมูลสลาก 10 ล้านใบได้โดยใช้ RAM ทำระบบ Search เพียง **~7.32 MB**
3. **ไม่มีปัญหาการแย่งตั๋วข้าม Pattern:** จัดการที่ระดับใบสลากจริงผ่าน Atomic Operation หมดปัญหา Race Condition 100%
4. **ความยืดหยุ่นของ Document Store:** การใช้ MongoDB ช่วยให้เก็บ Metadata ของสลาก (เช่น ประวัติงวด, โควตาตัวแทน, ข้อมูลผู้ถือ) ได้อย่างยืดหยุ่นโดยไม่กระทบความเร็วของระบบค้นหา

### ข้อแลกเปลี่ยนที่ยอมรับได้ (Acknowledged Trade-offs)

* **Search เป็น Eventual Consistency:** ตอนที่สลากใบสุดท้ายเพิ่งถูกจองไปสดๆ ร้อนๆ อาจมีเศษเสี้ยววินาทีที่หน้าค้นหายังบอกว่า "มีของ" แต่พอกดจองระบบจะแจ้งว่าถูกจองไปแล้วและสุ่มเลขที่ตรงเงื่อนไขตัวอื่นให้แทน ซึ่งเป็นพฤติกรรมปกติของระบบจองตั๋วสเกลใหญ่
